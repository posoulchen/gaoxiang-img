## ② 核心知识精讲
### 2.1 六项活动：配置管理的日常运转
教材把配置管理过程拆成六项活动，顺序要背下来，案例题写"应开展哪些配置管理活动"直接照抄：

**制定配置管理计划 → 配置项识别 → 配置控制 → 配置状态记录 → 配置审计 → 发布管理与交付**。

六项活动各自的产出不一样，这是选择题的抓手：

| 活动 | 核心产出 |
|---|---|
| 配置项识别 | 配置项清单、基线、配置库结构、标识规则 |
| 配置控制 | 变更后的新版本、检入检出记录、更新后的基线 |
| 配置状态记录 | 配置状态记录，通常以配置状态报告形式定期输出 |
| 配置审计 | 配置审计报告、不符合项清单与纠正要求 |
| 发布管理与交付 | 发布的版本包、交付记录、版本说明 |

一句话串起来：**识别定家底、控制管改动、状态报家底、审计验一致、发布交实物**。计划在最前面，因为管什么、谁管、放哪、怎么查，得先写清楚。

### 2.2 配置项识别与配置控制
**配置项识别**要做三件事，可以叫"三定"：

- **定项**：按规则选出哪些是配置项，形成配置项清单，明确每个配置项的负责人；
- **定基线**：确定建立哪几条基线、什么时点建立、由哪些配置项构成；
- **定标识**：给每个配置项唯一编号、版本号规则、存放位置，并搭好配置库的目录结构。

识别的输出如果只是一张清单，那是没做完——没有标识规则和库结构，后面所有控制都无从谈起。

**配置控制**是六项活动里最容易被考细的一项。它的动作链是：**变更申请 → 变更评估 → 决策审批 → 检出修改 → 验证 → 回检入库 → 版本升级 → 更新基线**。三个技术动作必须分清：

- **检出**：把配置项从受控库取到开发库，同时**加锁**，标记"此人正在修改"；
- **修改**：只在开发库进行，受控库中的原件保持不动；
- **回检**：修改完成、通过评审或测试后，把新版本提交回受控库，**解锁并升级版本号**。

加锁锁的是什么？锁的是"同一个配置项在同一时间只能有一个人修改"。两个人同时检出、先后回检，后回的会把先回的覆盖掉，而且没人知道——这就是案例里"公共类被覆盖、功能莫名丢失"的标准成因。命题人常在这里挖坑：把"检出"说成"复制一份出来改"，把"回检"说成"直接覆盖原文件"。

还要记住：配置控制不是独立王国，它和变更管理是一套流程的两段。变更管理负责"该不该改、谁批"，配置控制负责"批了之后怎么改、改完怎么入库、版本怎么升"。**没有经过批准的修改，配置管理员不能放行；没有进入配置库的变更，等于没改。**

### 2.3 配置状态记录与配置审计
**配置状态记录**要回答三个问题：现在是什么版本？谁在改、改到哪一步？历史上发生过哪些变更、结果如何？记录的结果通常以**配置状态报告**的形式定期输出，格式固定，是项目经理和 CCB 掌握"家底"的依据。案例里"项目经理不知道当前到底有几个版本在跑""客户问最新版是哪份，团队翻出三个目录"，缺的就是状态记录。

**配置审计**是今天的重中之重。它分两类，教材的措辞要咬住：

- **功能配置审计（FCA）**：验证配置项的**实际功能与性能**是否与**需求**一致。通俗说——"东西做对了没有"；
- **物理配置审计（PCA）**：验证配置项的**实际物理组成**是否与**配置标识（定义）**一致。通俗说——"东西齐不齐、版本对不对、文档全套在不在"。

| 维度 | 功能配置审计 FCA | 物理配置审计 PCA |
|---|---|---|
| 审什么 | 实际功能、性能与需求的一致性 | 实际组成、数量、版本与配置标识的一致性 |
| 典型问题 | 功能实现与需求不符、性能不达标 | 上线包缺模块、文档版本错、清单与实物不符 |
| 常见时点 | 基线建立前、测试与验收前 | 发布交付前、里程碑、变更实施后 |

审计的时点要记牢：**基线建立之前、发布或交付之前、重要里程碑、变更实施之后**。审计发现不符合项，不是"记一笔就算了"，而是要形成**不符合项清单**，明确纠正责任人和期限，纠正后**重新审计**直到关闭。

### 2.4 版本管理、变更追溯与配置管理员
**版本管理**的三条规矩：版本号唯一且可比较；旧版本必须保留、可回退；版本与变更单一对应，看到版本号就能查到对应的变更申请和审批记录。

**变更追溯**追的是一条链：需求 → 设计 → 代码 → 测试用例 → 发布包，每一环都能追到具体配置项和具体变更记录。追得动，才叫受控；追不动，就只是"存了一堆文件"。

**配置管理员的职责**，案例题里要能准确点名：

1. 建立并维护配置库，管理目录结构与访问权限；
2. 配置项的登记、标识与版本管理；
3. 执行配置控制，办理检出、回检与放行；
4. 编制并发布配置状态报告；
5. 组织或参与配置审计，跟踪不符合项关闭；
6. 负责配置库的备份与恢复；
7. 打包发布、办理交付，维护配置管理工具。

注意边界：配置管理员**不批准变更**（CCB 批），**不对功能是否正确负责**（测试与质量负责），**不决定项目做不做**（发起人与治理层决定）。他只是"账房先生 + 库管 + 审计组织者"。

> **记忆抓手**：识别定家底、控制管改动、状态报家底、审计验一致、发布交实物；FCA 看"功能对不对"，PCA 看"东西齐不齐"；检出加锁、回检升级，一个人一次只能改一项。

## ③ 高频易错点
1. **易错点**：把配置审计理解成"财务审计"或"质量检查" → **正解**：配置审计是验证配置项与需求、与配置标识的一致性，分**功能配置审计**和**物理配置审计**两类，与质量审计（过程审计）不是一回事。
2. **易错点**：认为 FCA 查文档齐不齐、PCA 查功能对不对 → **正解**：正好相反。**FCA 查功能与性能是否满足需求**；**PCA 查物理组成、数量、版本是否与配置标识一致**。
3. **易错点**：把"检出"理解为"从库里复制一份出来随便改" → **正解**：检出要**加锁**并登记，同一配置项同一时间只允许一人检出修改；修改完成后必须**回检**、验证并升级版本。
4. **易错点**：认为变更实施完就算结束 → **正解**：还要验证变更结果、回检入库、升级版本、更新基线与文档、更新配置状态报告，必要时开展配置审计，最后归档。
5. **易错点**：把配置状态报告当成"工作汇报" → **正解**：它记录的是**配置项当前状态与变更历史**（版本、修改人、修改时间、变更单号），是决策与追溯的依据，不是给领导看的成绩单。

**二、案例小问（1 题，14 分）**

【背景】某市医保支付方式改革信息系统升级项目，项目组 15 人，工期 10 个月。项目进行到第 6 个月的监理例会上暴露出几件事：测试组发现测试环境部署的程序与最新需求文档不一致，导致两轮回归测试作废；运维组收到的上线安装包里少了一个接口模块；两名开发人员同时修改同一个公共类，后提交的版本覆盖了前者的修改，且无人察觉；客户索要《接口设计说明书》最新版，项目经理从三个不同目录各找出一份，无法确认哪份有效；项目组从未开展过配置审计。

【问题1】请指出该项目在配置管理方面存在的主要问题。（5 分）
【问题2】结合配置管理过程，说明应如何整改。（6 分）
【问题3】说明功能配置审计与物理配置审计的区别，并指出"上线包缺少接口模块"应通过哪类审计发现。（3 分）

## ⑤ 参考答案与解析
**答案速查**：1.D　2.B　3.C　4.A　5.D　6.C　7.B　8.A

**1. D**　解析：需求跟踪矩阵的建立与维护属范围管理（收集需求）的工作，用来保证需求双向可追溯，不属于配置管理过程。A、B、C 与配置项识别、状态报告、配置审计一一对应，都是六项活动之一。

**2. B**　解析：功能配置审计验证配置项的实际功能与性能是否与需求一致。A 物理配置审计查的是物理组成、数量、版本与配置标识是否一致；C 质量审计审的是过程是否符合质量要求；D 状态报告是记录与报告，不是审计。

**3. C**　解析：缺模块、版本号与清单不符，属于"实际物理组成与配置标识不一致"，是物理配置审计的典型发现。A 功能配置审计关注功能性能是否满足需求；B 状态报告只能反映状态，不能验证一致性；D 过程分析属管理质量工具，不针对配置项组成。

**4. A**　解析：检出加锁保证同一配置项在同一时间只被一人修改，避免并行修改互相覆盖，从而保证版本唯一与可追溯。B 权限控制是另一项措施；C、D 与检出机制的设计目的无关。

**5. D**　解析：配置状态报告记录配置项的当前版本、变更历史、修改人与处理状态，是追溯和决策的依据。A 混淆了进度报告；B 与绩效考核无关；C 状态报告不能替代配置审计，二者目的不同。

**6. C**　解析：审批权在 CCB 或经授权的高层，配置管理员无审批权。A、B、D 均为配置管理员的常规职责。

**7. B**　解析：旧版本必须保留归档，可追溯、可回退；新版本登记版本号并关联对应变更单。A 删除旧版本会切断追溯链；C 让开发人员自行保管等于脱离配置库；D 把两个版本都放进产品库，会造成交付版本不确定。

**8. A**　解析：审计发现不符合项后应形成不符合项清单，明确纠正责任人与期限，纠正后重新审计直至关闭。B 只记录不纠正；C 改登记记录迁就实物，属于掩盖问题；D 配置管理必须跟踪关闭，不能一转了之。

**案例参考答案要点**

**问题1（5 分，答出五点即可）**
- **未建立（或未执行）配置管理计划**，配置项范围、基线、库结构、权限均不明确；
- **配置项标识不唯一、版本管理缺失**，同一文档存在多个版本，无法确定有效版本；
- **配置控制失效**，修改未经变更审批、未办理检出回检，出现**并行修改互相覆盖**；
- **未开展配置状态记录与报告**，项目组不掌握配置项当前版本与变更历史；
- **未开展配置审计**，需求文档、程序、安装包三者不一致长期未被发现；
- **配置库划分与权限不清**，开发库、受控库、产品库混用，上线包与受控版本脱节。

**问题2（6 分，按活动给分）**
- **制定并落实配置管理计划**：明确配置项清单、基线划分与建立时机、库结构、访问权限、版本规则与审计安排；
- **配置项识别**：为每个配置项建立**唯一标识 + 版本号 + 存放位置**，明确配置项负责人；
- **配置控制**：所有修改先提**变更申请**，经评估批准后由配置管理员放行，执行**检出加锁、回检升级**，禁止并行修改与直接覆盖；
- **配置状态记录与报告**：定期输出配置项当前版本、变更历史与待办变更，向项目经理与 CCB 报告；
- **配置审计**：在基线建立前、发布交付前、里程碑与变更实施后开展**功能配置审计与物理配置审计**，形成**不符合项清单**并跟踪关闭；
- **发布管理与交付**：从产品库统一打包发布，交付前核对**版本说明与配置清单**，确保上线包完整；
- 同步开展**配置管理工具与培训**，并把**外购组件与分包成果**纳入配置控制。

**问题3（3 分）**
- **功能配置审计**验证配置项的**实际功能与性能**是否与**需求**一致，回答"做得对不对"；
- **物理配置审计**验证配置项的**实际物理组成（数量、版本、文档齐套）**是否与**配置标识**一致，回答"齐不齐、是不是这一版"；
- "上线安装包缺少接口模块"属于实际组成与配置清单不一致，应通过**物理配置审计**发现。

**答题框架与标准话术**：第一段定性——"该项目**配置管理过程缺失，配置控制与配置审计未有效执行**"；第二段列问题——每条一句、动词开头，括号里挂关键词（标识唯一、检出加锁、状态记录、审计关闭）；第三段给措施——严格按"计划—识别—控制—记录—审计—发布"的顺序写，一条活动一条措施，末句补"并将**外购组件纳入配置控制**"。案例答案里不写"应该加强管理""提高认识"这类空话，阅卷只看关键词。
