## ② 核心知识精讲
### 2.1 配置管理到底管什么
教材给的配置管理定义，拆开看是四个动作：**标识**并记录配置项的功能和物理特性；**控制**这些特性的变更；**记录并报告**变更的过程与执行状态；**验证**配置项与规定需求的一致性。翻成项目管理的话：让项目里每一个要交付的东西都有唯一身份、有明确版本、改动有记录、状态可追溯。

它的作用可以归成五条，考场上看到"配置管理有什么用"就从这五条里挑：

- **完整性**：配置项不丢、不缺、不被偷偷改；
- **可跟踪性**：任何一个版本都能追到"谁改的、什么时候改的、为什么改、改了什么"；
- **支撑变更控制**：变更有明确的对象、有基线作参照、有边界可判断；
- **支撑质量与验收**：最终交付的一定是"经过评审和批准的那一版"，而不是某个人电脑里的那一版；
- **沉淀组织过程资产**：版本历史、变更记录本身就是可复用的经验。

这里必须先把一个高频混淆点摁死：**配置管理不是变更管理**。配置管理是"账本 + 仓库 + 审计"，管的是配置项的标识、状态、完整性和可追溯性；变更管理是"审批流程"，管的是"要不要改、谁批、怎么改、改完怎么验"。二者的关系是：配置管理为变更管理提供对象和记录，变更管理是配置控制得以落地的前提。一句话记住——**变更是"申请改动"，配置是"管住改动之后的样子"**。

### 2.2 配置项与三条基线
**配置项**是为配置管理设计的硬件、软件或两者的集合，在配置管理过程中作为一个**单个实体**来对待。判断标准很朴素：凡是要交付、要被控制、要被追溯的，都可以作为配置项。需求文档、设计文档、源代码、可执行程序、测试用例与测试报告、用户手册、部署脚本、接口说明、数据库脚本、第三方组件清单、项目计划与报告，统统算。

教材把它分成两类，这是选择题的常客：

- **基线配置项**：纳入基线、进入受控状态的配置项，如各类设计文档、源程序等，改动必须走变更控制；
- **非基线配置项**：不纳入基线但同样要管的，如项目的各类计划和报告，数量多、更新快，管理强度相对低。

判断口诀：**要交付、要当后续开发依据的进基线；日常管理的计划报告不进基线**。

每个配置项必须有"三件套"标识：**唯一标识**（编号或名称）、**版本号**、**存放位置**（在哪个库、哪个目录）。缺任何一件，追溯链当场断掉。

**基线**是一组配置项在项目生命周期不同时间点上，通过**正式评审**而进入**受控状态**的一个**特定版本**，是后续开发工作的基础。三条基线的对应关系，命题人最爱在这里挖坑：

| 基线 | 建立时点 | 主要内容 |
|---|---|---|
| 功能基线 | 系统分析与定义阶段结束，通过正式评审批准 | 系统规格说明书（系统层面的需求与任务要求） |
| 分配基线 | 需求分析阶段结束，通过正式评审批准 | 软件需求规格说明书 |
| 产品基线 | 组装与系统测试阶段结束，通过正式评审批准 | 产品全部配置项的规格说明（设计、程序、手册等） |

两个提醒。第一，**基线是"冻结线"，不是"完成线"**：基线建立之后照样能改，但必须走变更控制，批准后形成新的基线版本。第二，基线变更后要**同步更新基线内的所有相关配置项与文档**，否则就会出现经典事故现场——文档写的是 A，程序跑的是 B，测试测的是 C。案例题里"需求文档已更新，设计文档还是三个月前的版本"，考的就是这句。

> **记忆抓手**：功能基线卡"要什么"（系统规格），分配基线卡"分给谁做"（软件需求规格），产品基线卡"做成什么样"（产品规格）。三次评审、三条线、三次冻结。

### 2.3 三个配置库：权限一刀切开
配置库按"受控程度"分三层，这是整章最容易被拿来出情景题的地方：

| 配置库 | 定位 | 谁能动、怎么动 |
|---|---|---|
| 开发库（动态库） | 开发人员的工作区，存放正在开发、尚未评审的配置项 | 开发人员可自行检出、修改、回检，管理最松 |
| 受控库（主库） | 存放已通过评审、纳入基线的配置项 | 修改必须先提交变更申请，批准后由配置管理员放行，从受控库检出到开发库修改 |
| 产品库（静态库） | 存放已发布或待交付的最终产品 | 只读，入库后不得随意更改，交付时从这里取 |

流转方向是固定的：**开发库写 → 评审通过 → 进受控库 → 发布或交付 → 进产品库**。方向不能倒，层级也不能跳。

命题人常挖的三个坑：说"开发人员可以直接修改受控库中的配置项"（错，必须先变更、由配置管理员放行）；说"产品库里发现小问题可以顺手改掉"（错，产品库只读，改动要形成新版本、走变更）；说"配置管理员负责审批变更"（错，审批权在 CCB 或授权人，配置管理员负责执行配置控制、登记、状态报告与审计）。把这三句背下来，三个选项就废了。

### 2.4 配置管理计划与职责分工
配置管理计划是项目管理计划的从属计划，核心回答五个问题：

1. **管哪些**：配置项识别规则、配置项清单、基线划分与建立时机；
2. **谁来管**：配置管理组织与职责，配置管理员、CCB、各角色的权限边界；
3. **放在哪**：配置库的划分、目录结构、访问权限、备份与恢复策略；
4. **怎么管**：配置控制流程（申请→评估→审批→实施→验证）、版本规则、状态报告周期；
5. **怎么查**：配置审计的类型、时机、责任人与记录要求。

还有两项常被忽略、但案例里很好用：**配置管理工具与人员培训**、**分包商与供应商的配置管理要求**（外购件、第三方组件、开源组件也必须纳入配置控制，不能游离在账本之外）。

职责分工一句话：**CCB 决策，配置管理员执行，项目经理保障资源与流程落地，开发人员按规定检出回检**。谁越位谁就是案例里的错。

> **记忆抓手**：配置管理 = 一本账（配置项 + 基线）+ 三个库（开发 / 受控 / 产品）+ 五件事（识别、控制、状态记录、审计、发布）。

## ③ 高频易错点
1. **易错点**：把配置管理当成变更管理，以为配置管理就是"批变更" → **正解**：配置管理负责标识、状态记录、完整性与可追溯；变更管理负责变更的申请、评估、决策、实施与验证。二者衔接但职责不同。
2. **易错点**：认为基线建立后就不能再改 → **正解**：基线可以改，但必须走变更控制，经批准后形成新的基线版本，并同步更新基线内所有相关配置项与文档。
3. **易错点**：把分配基线对应到《系统规格说明书》 → **正解**：分配基线对应《软件需求规格说明书》；《系统规格说明书》通过评审形成功能基线；产品规格说明对应产品基线。
4. **易错点**：认为产品库里的配置项发现缺陷可以就地修改 → **正解**：产品库只读；任何修改都要形成新版本、走变更控制、重新评审入库，旧版本归档保留。
5. **易错点**：认为配置管理员有权批准变更或决定变更是否实施 → **正解**：审批权在 CCB 或经授权的高层；配置管理员负责放行、登记、状态报告、组织配置审计和发布打包。

## ⑤ 参考答案与解析
**答案速查**：1.B　2.B　3.A　4.D　5.C　6.B　7.A　8.C

**1. B**　解析：配置管理的定义就是标识并记录配置项特性、控制变更、记录报告变更状态、验证与需求一致。A 是项目监控与整体管理的目标；C 是变更管理与 CCB 的职责；D 只是配置管理带来的一个便利，不是目标本身，且"最新版本"不等于"受控版本"。

**2. B**　解析：需求分析阶段结束、评审批准《软件需求规格说明书》，建立的是分配基线。A 功能基线在系统分析与定义阶段结束建立，对应系统规格说明书；C 产品基线在组装与系统测试阶段结束建立；D 教材没有"质量基线"这一基线类型。

**3. A**　解析：非基线配置项指不纳入基线、但需要管理的配置项，如各类项目计划和报告。B、C、D 都是要作为后续开发依据、进入受控状态的基线配置项。

**4. D**　解析：受控库中的配置项修改必须先走变更控制，批准后由配置管理员放行，检出到开发库修改。A 跳过变更审批；B 用覆盖方式提交，破坏了版本完整性和可追溯性；C 属未受控修改，任何人事后都无法追溯。

**5. C**　解析：产品库（静态库）存放已发布或待交付的最终产品，原则上只读。A 开发库是开发人员工作区；B 受控库存放已通过评审、纳入基线的配置项；D 备份库不是配置库的划分类型。

**6. B**　解析：成本基准的编制方法、资金需求属成本管理与制定预算的内容，不写进配置管理计划。A、C、D 分别对应配置管理计划的"管哪些、放在哪、怎么查"，都是标准内容。

**7. A**　解析：基线变更后必须同步更新基线内所有相关配置项与文档，并形成新的基线版本，否则配置项之间的对应关系断裂，可追溯性丧失。B、C 把"客户不追究"当成合规标准；D 只在报告中注明而不更正内容，问题依然存在。

**8. C**　解析：产品库只读，修改必须走完变更控制，且改动在开发库完成、评审后进受控库、发布后形成新的产品库版本。A 破坏产品库只读属性；B 跳过评审与变更记录；D 自建临时库等于脱离配置管理，无法追溯。题干中的数量只是背景，配置库的受控级别才决定路径。

**判断改错题参考答案**

（1）**错误**。配置管理负责配置项的标识、状态记录、完整性与可追溯性；**变更的审批**属于变更管理，由 **CCB** 决策。二者相互衔接，但不是同一件事。

（2）**错误**。基线可以修改，但必须经过**变更控制**，批准后形成**新的基线版本**，并同步更新基线内的相关配置项与文档。

（3）**正确**。《系统规格说明书》在系统分析与定义阶段结束通过正式评审批准后，形成**功能基线**。

（4）**正确**。受控库中的配置项处于受控状态，修改须提交**变更申请**，经**评估与批准**后由**配置管理员**放行，检出到开发库修改。

（5）**错误**。审批权在 **CCB**（或经授权的高层），配置管理员负责配置控制的执行、登记、状态报告与审计，无权批准变更。
